# REVIVE Claims Audit

This document reviews the product and technical claims made across the repository, UI, and documentation, classifying them by their level of support in the current implementation.

## 1. Directly Supported Claims

- **"Prediction is probabilistic. Policy is deterministic. Execution is auditable."**
  - **Status:** DIRECTLY SUPPORTED.
  - **Evidence:** `HierarchicalPredictor` returns probabilities. `DeterministicPolicyEngine` returns explicit boolean approvals based on hardcoded rules (e.g., `budget_remaining`). `SimulatedExecutionAdapter` ensures only policy-approved actions run. `AuditLogger` generates an immutable ledger of all steps.

- **"REVIVE maintains a strict, append-only chronological audit trail of all automated decisions."**
  - **Status:** DIRECTLY SUPPORTED.
  - **Evidence:** The `RecoveryTrace` model and `AuditLogger` record every state transition, actor, and payload accurately.

- **"The simulator cleanly isolates RNG streams, ensuring fair evaluation of policies."**
  - **Status:** DIRECTLY SUPPORTED.
  - **Evidence:** Fixed in Phase 8/9. The `OutcomeEngine` uses a dedicated `random.Random` instance seeded uniquely per mandate to prevent inter-strategy contamination.

- **"On the locked synthetic benchmark, the calibrated ML policy reproduced the exact same decisions as the historical heuristic."**
  - **Status:** DIRECTLY SUPPORTED.
  - **Evidence:** Phase 8 experiment locked results: ₹INVALIDATED (49,495.05) for ML Probability vs ₹INVALIDATED (49,495.05) for Smart Heuristic (0.00% incremental lift). Both selected the same candidate action for 100% of mandates.

## 2. Supported with Qualification

- **"REVIVE recovers failed recurring payments."**
  - **Status:** SUPPORTED WITH QUALIFICATION.
  - **Qualification:** Must specify that this is demonstrated in a *simulated* environment. REVIVE currently simulates recoveries to test decisioning architectures.

- **"The ML model predicts the probability of recovery."**
  - **Status:** SUPPORTED WITH QUALIFICATION.
  - **Qualification:** The ML model (`Pipeline` over `HistGradientBoostingClassifier`) correctly generates calibrated probability estimates based on point-in-time features, but it was trained on *synthetic* data generated by the `DataGenerator`. It has not been validated on real-world bank data.

## 3. Unsupported / Should Be Removed

- **"REVIVE integrates with Razorpay to automate recoveries."**
  - **Status:** UNSUPPORTED.
  - **Action:** Any language implying live Razorpay execution has been removed. The README explicitly states "no live payment gateway (no real Razorpay API)".

- **"The ML strategy outperforms traditional retry methods."**
  - **Status:** UNSUPPORTED.
  - **Action:** Explicitly removed. The documentation and UI prominently display the 0.00% lift metric and explain that the heuristic tied the ML policy.

- **"REVIVE uses reinforcement learning (RL) or contextual bandits to optimize retries."**
  - **Status:** UNSUPPORTED.
  - **Action:** All mentions of RL/bandits as implemented features have been scrubbed. The system currently uses standard probabilistic classification (Expected Value/Probability maximization) mapped against a deterministic policy.


## 4. Benchmark Result Update

The earlier 49,495.05 artifact was invalidated after a provenance audit showed it had been generated before stable RNG implementation and cross-process RNG tests were established. The corrected benchmark uses SHA-256 stable seeding (with deterministic UUIDs) and produces:

Smart = ₹50,192.12
ML = ₹50,192.12
Lift = 0.00%
